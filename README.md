# Telegram-бот АО «Узбекгидроэнерго»

Бот приёма **обращений граждан** и **жалоб на коррупцию** (с анонимной подачей).
Мультиязычный (5 локалей), с ролевой маршрутизацией обращений ответственным
лицам, статусами, ответами заявителю и аудитом.

## Возможности

- 🌐 5 языков: русский, каракалпакский, узбекский (кириллица и латиница), английский. Выбор при `/start`, смена в любой момент.
- 📝 Обращения граждан и 🛡 жалобы на коррупцию через пошаговую форму (ФИО, телефон, текст, фото/документы — включая альбомы).
- 🕵 **Анонимная** подача жалоб: ФИО/телефон не сохраняются; tg_id заявителя хранится только в зашифрованном виде (ключ — вне БД), ответ доставляется push.
- 📋 «Мои обращения» — статусы своих обращений (анонимные не показываются).
- 👥 Ответственные лица получают карточку обращения, могут «взять в работу» (атомарно, кто первый), ответить и закрыть; ответ пересылается заявителю на его языке.
- 🗂 **Реестр заявок** для ответственных и админов: список своих типов с фильтром по статусу, сортировкой и постраничной навигацией; из карточки списка доступны те же действия (взять / ответить / закрыть). Пункт меню и команда (`/appeals`, `/complaints`) видны только тем, у кого есть роль.
- 🔐 Полный аудит действий (смена статусов, назначения ролей, ответы) без PII.
- 🚦 Антифлуд (throttling), PII-safe логирование.

## Стек

Python 3.11+, aiogram 3.x, aiogram-i18n + Fluent, PostgreSQL (SQLAlchemy 2.0 async + asyncpg) + Alembic, Redis (FSM + throttling), Docker. Запуск — polling (тест) или webhook (прод).

## Конфигурация (`.env`)

Скопируйте `.env.dist` → `.env` и заполните:

- `BOT_TOKEN` — токен от @BotFather;
- `ADMIN_IDS` — Telegram ID администраторов (через запятую);
- `ANON_ENC_KEY` — сгенерируйте: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`;
- `POSTGRES__HOST/PORT/USER/PASSWORD/DB`, `REDIS__HOST/PORT/PASSWORD/DB` — реквизиты внешних БД и Redis;
- для прода: `USE_WEBHOOK=true`, `WEBHOOK_URL` (HTTPS), `WEBHOOK_SECRET`.

**Миграции применяются автоматически при старте бота** (`alembic upgrade head` внутри процесса). На старте бот ждёт готовности БД с ретраями. Это удобно для одиночного процесса/контейнера. Если у вас несколько реплик — выставьте `RUN_MIGRATIONS_ON_STARTUP=false` и применяйте миграции отдельным шагом (`alembic upgrade head`), чтобы реплики не гонялись за апгрейд.

## Деплой на веб-панели (один контейнер)

Целевой прод — **один контейнер бота** на хостинг-панели, где PostgreSQL и Redis уже предоставлены панелью (compose не нужен):

1. Соберите образ из этого репозитория (`Dockerfile`) средствами панели или `docker build -t anticor-bot .`.
2. Задайте переменные окружения контейнера: `BOT_TOKEN`, `ADMIN_IDS`, `ANON_ENC_KEY`, и реквизиты панельных сервисов — `POSTGRES__HOST/PORT/USER/PASSWORD/DB`, `REDIS__HOST/PORT/PASSWORD/DB`. Для webhook-режима — `USE_WEBHOOK/WEBHOOK_URL/WEBHOOK_SECRET`.
3. Команда запуска контейнера — стандартная из образа: `python -m bot`. Бот сам накатит миграции на старте и подключится к внешним БД/Redis.
4. Поставьте контейнеру политику авто-рестарта (панель обычно это умеет) — если БД ещё не готова, бот переподнимется.

> Образ запускает **один долгоживущий процесс** и не публикует портов (для webhook TLS терминируйте на reverse-proxy панели). Никакого отдельного «migrate»-шага не требуется.

## CI/CD (GitHub Actions)

`.github/workflows/deploy.yml` на каждый push в `main`:

1. **test** — `ruff` + `pytest` (с сервисным Postgres; конкурентные тесты идут против реальной БД через `TEST_PG_DSN`).
2. **build-and-push** — сборка Docker-образа и пуш в Docker Hub с тегами `latest` и `:<sha8>` (кэш через GitHub Actions).
3. **verify-image** — скан образа Trivy (CRITICAL/HIGH, fixed-only).
4. **rebuild-no-cache** — если скан нашёл уязвимости, пересборка без кэша и повторный скан.
5. **trigger-watchtower** — дёргает Watchtower на сервере, тот подтягивает свежий образ и пересоздаёт контейнер бота.

**Деплой:** первый раз контейнер бота создаётся на панели **вручную** (см. «Деплой на веб-панели»); дальше каждый push в `main` обновляет его автоматически через Watchtower.

Нужные **GitHub Secrets**:

| Secret | Назначение |
| --- | --- |
| `DOCKERHUB_USERNAME` | логин Docker Hub (он же префикс имени образа `…/anticor-bot`) |
| `DOCKERHUB_TOKEN` | access-token Docker Hub |
| `WATCHTOWER_HOST` | хост Watchtower-эндпоинта (без `https://`) |
| `WATCHTOWER_SECRET` | Bearer-токен Watchtower API |

## Локальная разработка (Docker Compose)

`docker-compose.yml` поднимает Postgres + Redis + бота вместе — только для разработки:

```bash
make up      # docker compose up -d --build
make logs    # docker compose logs -f bot
make down
```

## Локальный запуск (без Docker)

```bash
make install
# поднимите PostgreSQL и Redis, заполните .env (POSTGRES__HOST=localhost ...)
make run      # миграции накатятся на старте автоматически
```

## Разработка

- `make lint` — ruff.
- `make test` — pytest. Конкурентные тесты идут против реального Postgres: задайте `TEST_PG_DSN=postgresql+asyncpg://...`, иначе они пропускаются.
- `make migration m="описание"` — новая Alembic-ревизия.

## Назначение ответственных

Администратор (из `ADMIN_IDS`) использует команды бота:

- `/assign` — переслать сообщение пользователя или указать его ID, затем выбрать тип ответственности (обращения / жалобы).
- `/responsibles` — список ответственных и снятие ролей.

После назначения/снятия роли персональное меню команд пользователя обновляется автоматически: у ответственного появляется `/appeals` и/или `/complaints`, при снятии последней роли — возвращается общий список команд.

## Безопасность и приватность (важно для прод)

- **Анонимность** защищает от утечки через дамп БД (нет открытого автора у анонимной жалобы). Она **не** защищает от оператора, владеющего `ANON_ENC_KEY`: храните ключ в секрет-сторе/KMS, отдельно от БД-бэкапов; ограничьте доступ. Возможна слабая временна́я корреляция (`users.created_at` vs `submissions.created_at`).
- **Вложения**: EXIF/метаданные фото не вырезаются — пользователь предупреждается; для повышенной приватности можно добавить стрипинг.
- **Webhook**: бот слушает `127.0.0.1`; TLS терминируйте на reverse-proxy, наружу публикуйте только прокси. Секрет (`WEBHOOK_SECRET`) высокоэнтропийный, путь непредсказуемый.
- **Бэкапы БД** содержат персональные данные обращений — шифруйте и ограничивайте доступ.
- **Каракалпакские** формулировки — рабочие; перед прод-запуском рекомендуется вычитка носителем (помечено `# TODO: вычитка носителем`).
