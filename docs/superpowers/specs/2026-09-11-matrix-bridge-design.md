# Мост в Matrix (Element) для ответственных — дизайн

**Дата:** 2026-09-11 · **Проект:** anticor-bot · **Статус:** на утверждении

## Проблема

На рабочих компьютерах организации Telegram заблокирован. Ответственные лица
получают push-карточки только в Telegram — значит, в рабочее время они не видят
новых заявок и не могут на них реагировать. У организации уже есть свой
Matrix-сервер (Synapse) с клиентом Element, которым сотрудники пользуются.

Нужно: карточки заявок попадают в комнату Element, и там же можно **взять,
ответить и закрыть** — с теми же правами, той же атомарностью и тем же аудитом,
что и в Telegram.

## Ключевой принцип

**Matrix — новая точка входа к существующим правам, а не новые права.**
Тот же принцип, что у реестра ([2026-08-06-submissions-registry-design.md](2026-08-06-submissions-registry-design.md)).

Каждое действие из Element выполняется **от имени существующего `User`**. Это
не удобство, а необходимость: `SubmissionStatusEvent.actor_user_id`,
`SubmissionResponse.responder_user_id`, `try_claim(user_id)`, `close(user_id)` —
всё требует `users.id`. Комната сама по себе никого ни на что не уполномочивает.

| | Push-карточка (Telegram) | Комната Element |
|---|---|---|
| Кто видит | `resp_<type>` | участники комнаты типа, **привязанные** к `User` с `resp_<type>` |
| Авторизация | `_authorize()` по `User` | **тот же** код по **тому же** `User` |
| Взять / ответить / закрыть | хендлеры `responsible.py` | **те же** сервисные операции |
| Аудит | `actor_user_id` | `actor_user_id` (привязанный `User`) |
| Анонимка | `🕵 Анонимно` + текст | то же самое, тем же `render_card` |

Ни одна строка не становится видимой тому, кто не увидел бы её в карточке, и ни
одно действие не проходит мимо `can_handle_type()` / проверки владельца.

## Объём

### Входит

1. **Привязка** Matrix-аккаунта к `User` по одноразовому коду (самообслуживание).
2. **Две комнаты** — по типу заявки (`appeal`, `corruption`); карточка новой
   заявки уходит в комнату её типа вместе с вложениями.
3. **Действия из комнаты**: взять в работу, ответить заявителю (текст),
   закрыть, повторно открыть карточку, справка. Всё — через reply на карточку.
4. **Синхронизация статуса**: изменение из любого канала обновляет карточки во
   всех каналах (Telegram-карточки у ответственных **и** карточка в комнате).
5. Локализация сообщений комнаты через Fluent (локаль комнаты — настройка,
   по умолчанию `uz_latn`).

### Не входит (явно отложено)

Реестр/поиск из комнаты · вложения в ответах из Element · эхо текста ответа в
другой канал (в Telegram карточки и сейчас не показывают ответы — паритет) ·
отвязка Matrix самим пользователем (только админом) · несколько комнат на один
тип · E2EE-комнаты.

## Модель доступа

### Привязка Matrix ↔ User

```
Telegram, ответственный:   /matrix        → бот выдаёт код, например A7K2M (TTL 10 мин)
Element, тот же человек:   !link A7K2M    → бот привязывает отправителя (@x:gidro.uz) к этому User
```

- Код хранится в **Redis** (`matrix:link:<code>` → `users.id`, TTL 10 минут);
  таблица не нужна, Redis уже есть. Код одноразовый — удаляется при
  использовании. Генерируется из алфавита без похожих символов (`0/O`, `1/I`).
- `users.matrix_id` — новая колонка, `String(255)`, `unique`, `nullable`.
  Один Matrix-аккаунт ↔ один `User`. Повторный `!link` **переносит**
  привязку на нового `User` (старая обнуляется) — это позволяет исправить
  ошибку без админа; событие пишется в аудит (`matrix_linked`,
  `meta="rebind"`), без PII.
- `/matrix` доступен только `IsResponsible | IsAdmin` — обычному заявителю
  привязка не нужна и не предлагается.
- Отвязка: `/matrix_unlink <tg_id>` (админ). Аудит `matrix_unlinked`.
- Отправитель без привязки, что бы ни написал в комнате, получает одно
  сообщение-подсказку (`!link`) и ничего больше.

### Комнаты по типам

`MATRIX__ROOM_APPEAL` и `MATRIX__ROOM_CORRUPTION` — два ID комнат. Карточка
заявки уходит **только** в комнату своего типа. Состав комнат ведут админы
организации в Element, но **членство в комнате не даёт прав**: на каждое
действие бот заново проверяет `can_handle_type(linked_user, sub.type)` и, для
ответа/закрытия, владельца (`assigned_to_user_id in (None, user.id)` или
админ) — ровно как `_authorize()` в `responsible.py`. Тип берётся из строки
заявки, а не из комнаты: даже если карточка появится не в той комнате,
чужой тип не пройдёт.

Комнаты **без сквозного шифрования**: бот должен читать reply'и. Это
организационное требование, фиксируется в README.

### Анонимность

Инвариант не затрагивается. Карточка рендерится тем же `render_card()`
(для анонимной — без ФИО/телефона). Ответ заявителю уходит через тот же
`resolve_author_chat_id()` — `enc_chat_ref` расшифровывается в памяти и
никогда не покидает процесс. Мост **не читает** `anon_delivery_refs`.

Честная оговорка (как и для Telegram): текст заявки и вложения попадают в
историю комнаты, то есть в БД Synapse. Это то же самое, что сейчас происходит
с чатами ответственных в Telegram, — новый канал, не новый класс риска.
Synapse — сервер организации, Telegram — нет; экспозиция скорее уменьшается.

## Архитектура

### 1. Вынос действий в сервисный слой (рефакторинг)

Сейчас последовательности «взять», «закрыть», «ответить» живут в
`handlers/responsible.py` и завязаны на `CallbackQuery`. Чтобы Matrix не
дублировал их (правило проекта: *actions are not reimplemented*), они
переезжают в `bot/services/actions.py`:

```python
class SubmissionActions:
    def __init__(self, session, bot, core, cipher, default_locale): ...

    async def authorize(self, sub_id, user, *, require_owner=False) -> Submission | None
    async def take(self, sub, user)   -> TakeResult   # won | already_taken(name)
    async def close(self, sub, user)  -> bool         # False если уже закрыта
    async def reply(self, sub, user, text) -> bool    # False если заявитель недоступен
```

Каждая операция делает **ровно то, что делает сегодняшний хендлер**, в том же
порядке: атомарный UPDATE → status event → audit → `commit` → сетевой fan-out
(`update_all_cards`, уведомление заявителя) → `commit`. Правило «commit до
fan-out» сохраняется. `responsible.py` становится тонким адаптером: разбор
`CallbackQuery` → вызов `SubmissionActions` → `query.answer(...)` →
`registry.refresh_detail(...)`. Поведение Telegram не меняется — это
проверяют существующие `test_handlers_flow.py` / `test_responsible_admin.py`.

`update_all_cards()` расширяется: помимо Telegram-доставок обновляет
карточку в Matrix (см. п. 3). Так одно и то же изменение статуса видно везде.

### 2. Пакет `bot/matrix/`

```
bot/matrix/
  client.py    — обёртка над matrix-nio: login, sync-loop, send/edit/upload,
                 авто-принятие приглашений; знает только про Matrix
  bridge.py    — логика: карточка заявки, разбор reply/команд, вызов
                 SubmissionActions; знает про заявки, не знает про nio-детали
  link.py      — коды привязки (Redis) и команда !link
  render.py    — карточка + подсказки для комнаты (поверх render_card),
                 HTML ↔ plain для formatted_body
```

Зависимость одна: `bridge.py` → `services/actions.py`. Хендлеры Telegram
**не** импортируют `bot.matrix`; `bot.matrix` **не** импортирует
`bot.handlers`. Обе стороны встречаются только в сервисном слое. Проверяется
тестом, как для `registry.py` ↔ `responsible.py`.

### 3. Данные

Миграция Alembic (одна ревизия):

- `users.matrix_id` — `String(255) NULL UNIQUE`.
- `matrix_deliveries` — куда именно ушла карточка, чтобы её редактировать и
  чтобы reply на неё резолвился в заявку:

  | колонка | тип | смысл |
  |---|---|---|
  | `id` | int PK | |
  | `submission_id` | FK submissions, ON DELETE CASCADE, index | |
  | `room_id` | String(255) | комната |
  | `event_id` | String(255) | событие в комнате |
  | `kind` | String(16) | `card` (основная карточка) · `attachment` · `note` |
  | `created_at` | timestamptz | |
  | уникальность | `(room_id, event_id)` | |

  Reply на **любое** из этих событий (карточку, вложение, служебную заметку
  бота) резолвится в заявку. Редактируется только `kind='card'`.

Хранение секретов: только через `Settings` (`SecretStr`), как и остальные.

### 4. Рантайм

Мост — фоновая `asyncio`-задача в том же процессе, что polling/webhook
(запускается из `bot/__main__.py` после `core.startup()`). Один процесс, один
образ, никакого второго логина в Telegram.

Matrix-события — не Telegram-апдейты, middleware цепочка на них не работает.
Мост получает `async_sessionmaker` и на **каждое** событие открывает свою
сессию (`async with session_pool() as session`) — commit при успехе, rollback
при исключении, как `DbSessionMiddleware`. Одно событие — одна транзакция.

Если Matrix недоступен (нет сети, неверный пароль) — бот **работает без
него**, пишет `ERROR` в лог и периодически пытается переподключиться.
Недоступность Matrix никогда не мешает приёму заявок и Telegram-каналу.

Старые события: при старте sync отдаёт историю комнаты; события с
`origin_server_ts` раньше старта игнорируются (иначе бот «ответил бы» на
недельной давности reply). Собственные события бота игнорируются.

### 5. Поток данных

**Новая заявка** (`handlers/submission.py`, после существующего commit и
`dispatch_to_responsibles`):

```
commit → dispatch_to_responsibles (как сейчас)
      → bridge.post_submission(sub):
            карточка (render_card в локали комнаты + подсказки) → matrix_deliveries(kind=card)
            вложения: bot.download(file_id) → client.upload → m.image / m.file
                      → matrix_deliveries(kind=attachment)
```

Вложения — ограничение Telegram Bot API 20 МБ на скачивание; крупнее —
пропускается с пометкой в карточке. Ошибка отправки в Matrix логируется и
**не** откатывает заявку (она уже закоммичена и разослана в Telegram).

**Действие из Element** (reply на карточку/вложение):

```
событие → не бот, не старое, в одной из двух комнат
        → matrix_deliveries: event_id → submission_id   (иначе игнор — обычная беседа)
        → users.matrix_id = sender → User                (иначе подсказка !link, стоп)
        → команда?  !olish  → actions.take
                    !yopish → actions.close
                    !karta  → перепостить актуальную карточку
                    иначе (текст) → actions.reply (require_owner)
        → результат → реакция 👍 / сообщение об ошибке reply'ем в комнате
        → карточка в комнате перерисовывается (статус, исполнитель)
```

`actions.*` сами обновляют Telegram-карточки и уведомляют заявителя — мост
об этом не знает, как не знает и `registry.py`.

**Действие из Telegram** → `actions.*` → `update_all_cards` → в том числе
`matrix_deliveries(kind=card)` редактируется (`m.replace`). Статус и
исполнитель в комнате всегда актуальны.

Осознанное отличие: в Telegram `update_all_cards` **заменяет** карточку
короткой строкой статуса и убирает кнопки (так сделано сейчас, не меняем).
В комнате карточка перерисовывается **целиком** — текст заявки остаётся
виден, меняются строка статуса, исполнитель и набор подсказок (после закрытия
остаётся только `!karta`). В комнате нет кнопок, которые нужно было бы убрать,
а история переписки в Element — единственное место, где команда видит заявку.

### 6. Команды в комнате

Префикс `!` (в Element `/` занят клиентом). Все — reply'ем на карточку, номер
указывать не нужно; допускается и `!olish <public_id>`.

| Команда | Действие | Права |
|---|---|---|
| `!link КОД` | привязать аккаунт | любой участник |
| `!olish` | взять в работу (атомарно) | `resp_<type>` \| admin |
| `!yopish` | закрыть, уведомить заявителя | владелец \| admin |
| `!karta` | перепостить актуальную карточку | `resp_<type>` \| admin |
| `!yordam` | справка | любой |
| текст reply'ем | ответ заявителю на его языке | владелец \| admin |

Подсказки с этими командами печатаются под каждой карточкой (в Element нет
inline-кнопок). Никаких новых прав: таблица — подмножество того, что есть на
Telegram-карточке.

### 7. Локализация

Все новые строки — через Fluent, добавляются во **все пять** `.ftl`
(`test_i18n.py` требует паритет). Локаль комнаты — `MATRIX__LOCALE`
(по умолчанию `uz_latn`); карточка и служебные сообщения комнаты — в ней.
Ответ заявителю — по-прежнему в **его** локали (`_author_locale`), это не
меняется. Сообщения `/matrix` в Telegram — в локали пользователя.

### 8. Конфигурация

```
MATRIX__HOMESERVER=https://matrix.uzgidro.uz:30443
MATRIX__USER=@anticorbot:gidro.uz
MATRIX__PASSWORD=…            # или MATRIX__TOKEN
MATRIX__ROOM_APPEAL=!…:gidro.uz
MATRIX__ROOM_CORRUPTION=!…:gidro.uz
MATRIX__LOCALE=uz_latn
MATRIX__STORE_DIR=/app/matrix_store   # состояние nio; в контейнере — volume
```

`MatrixSettings` — вложенная pydantic-модель (`__`), пароль/токен —
`SecretStr`. `settings.matrix.enabled` = задан homeserver **и** user **и**
(password или token). Пустая конфигурация = мост выключен, ничего не
ломается — так текущий прод обновится без изменений поведения.

### 9. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Matrix недоступен при старте | лог `ERROR`, бот работает без моста, ретраи с backoff |
| Sync-loop упал | лог, перезапуск задачи с backoff; Telegram не затронут |
| Не удалось отправить карточку | лог `WARNING`; заявка уже сохранена и разослана в Telegram |
| Вложение > 20 МБ / ошибка скачивания | пометка в карточке, остальные вложения отправляются |
| Заявитель заблокировал бота | как сейчас: `safe_send` → False → сообщение в комнате «не доставлено» |
| Reply от непривязанного | одна подсказка `!link`, действие не выполняется |
| `!olish` проигран (уже взяли) | сообщение «уже взял <имя>» — как `cb-already-taken` |
| Редактирование карточки: `not modified` | игнорируется |

Логи моста проходят через тот же `security/logging.py` — текст заявок и
имена в логи не попадают.

### 10. Тесты

- `tests/test_actions.py` — вынесенные операции: take (won / lost), close
  (open / already closed), reply (author reachable / not), порядок commit →
  fan-out. SQLite-режим, как остальные unit-тесты; атомарность по-прежнему
  доказывают Postgres-тесты `test_concurrency.py` (репозиторий не меняется).
- `tests/test_matrix_bridge.py` — фейковый nio-клиент: карточка и вложения
  уходят в нужную комнату; reply резолвится через `matrix_deliveries`;
  непривязанный → подсказка; `can_handle_type` и владелец соблюдаются; старые
  и собственные события игнорируются; статус из Telegram редактирует карточку.
- `tests/test_matrix_link.py` — код в Redis (fakeredis или подмена): выдача,
  TTL, одноразовость, перепривязка, `/matrix` только для ролей.
- `test_i18n.py` — паритет ключей пройдёт автоматически после добавления.
- Архитектурный тест: `bot.matrix` не импортирует `bot.handlers`, и наоборот.
- Существующие тесты хендлеров — без изменений: они и есть доказательство,
  что рефакторинг не поменял поведение Telegram.

### 11. Развёртывание

- Зависимость `matrix-nio` (без `[e2e]` — комнаты не шифруются, `libolm` не
  нужен). Образ: `Dockerfile` копирует `bot/` целиком — новый пакет попадёт
  сам, `.dockerignore` не трогаем. Trivy: `matrix-nio` тянет `aiohttp`,
  `h11`, `jsonschema` — те же семейства, что уже есть.
- Миграция применяется на старте (`RUN_MIGRATIONS_ON_STARTUP=true`), как все.
- `MATRIX__STORE_DIR` — примонтировать volume, чтобы состояние sync не
  терялось при пересоздании контейнера (иначе бот при каждом старте будет
  перечитывать историю; безопасно благодаря фильтру по времени, но шумно в логах).
- Организационно: создать аккаунт `@anticorbot` на homeserver, две комнаты без
  шифрования, пригласить бота (приглашения он принимает сам и пишет ID
  комнаты), заполнить `MATRIX__*` в переменных контейнера.
- Ветка `feature/matrix-bridge` → Pull Request → merge в `main` = деплой.
  Прямых push в `main` нет.
